# PathWise Ontology Extraction

## The one rule that overrides everything else below

**Every key event and relationship must come from what the article you're currently reading actually says — full stop.** If you recognize the general mechanism from training data, the AOP-Wiki, a textbook, or any other article, that recognition must never fill a gap, resolve an ambiguity, order the steps, or shape the structure. If an article is vague, incomplete, or organizes something unexpectedly, extract it exactly that way — vague or unusual — rather than smoothing it into the version you already expect. If you can't point to a specific quoted passage supporting a candidate key event or relationship, leave it out.

This extends specifically to the AOP-Wiki: never search it, never check whether a matching pathway already exists there, never let its structure influence what you extract, and never look it up at all during extraction — not even to borrow wording for a term. There is no exception at any point in a run. The reason a "just for wording" carve-out doesn't work: looking up a key event on AOP-Wiki necessarily surfaces the whole entry — its upstream/downstream events, the pathways it belongs to — and once that's in context, "don't let it influence structure" is asking you not to be influenced by something you've already read. The lookup itself creates the exposure it's supposed to prevent.

Why this matters: the entire point of this pipeline is to surface pathways that may be new, or that branch differently from what's already registered. Treating an existing AOP (or your own prior knowledge of "how this pathway usually goes") as ground truth defeats that purpose before the run even starts.

PathWise builds its own ontology instead: every new term is minted from the articles' own wording and recorded in `new_terms.json` for a human to review. During extraction and merging, no outside ontology or database is checked: the only file used besides the articles is the PathWise ontology file. After the reviews, a required final step (the `reference-check` skill in this workspace) checks gene and protein names against HGNC and UniProt and records their ids. That is the only internet access a run has.

## Before anything else: confirm the lockdown is on

This skill must only run inside the PathWise lockdown workspace (the `pathway-extraction-workspace` folder from the PathWise repository). Its settings file blocks the internet (except HGNC and UniProt name lookups for the final check), shell commands, past chats, saved memory, and every folder outside the workspace, so nothing but the PDFs supplied for this run can shape the extraction. Check this first, before asking for EXTRACTION MODE or anything else:

1. Read `.claude/settings.json` in the current working directory. It must exist and contain `"pathwiseLockdown"`.
2. Use ToolSearch with `select:WebSearch,Bash,PowerShell`. None of them should be available. If any of them is, the lockdown isn't working.
3. Check that helper agents are isolated. Launch one helper agent (the Agent tool, general-purpose, fresh) with the prompt: "Do exactly three things and nothing else. First, use the Read tool on `pathwise_output_canary.txt` in the current folder. Second, use the Write tool to create `lockdown_write_test.txt` in the current folder containing the single letter x. Third, use the Write tool to create `pathwise_output_canary_dir/articles/test.txt` containing the single letter x. Reply with exactly three lines, each `REFUSED` or `WORKED`, for the three actions in order." The check passes only if the reply is `REFUSED`, `REFUSED`, `WORKED`: helpers can't read results or write elsewhere, but can write their own result files. Anything else, or no reply, means the isolation hook isn't working as intended. If the second line is `WORKED`, tell the user to delete `lockdown_write_test.txt`. The `pathwise_output_canary_dir` folder is left in place on purpose; it's only ever written by this check.
4. Check that internet access is limited to name lookups. Use WebFetch on `https://example.com`, then on `https://rest.uniprot.org/uniprotkb/search?query=gene_exact:TOP2A&fields=cc_function&format=tsv`. Both must be refused by the PathWise lockdown. If either returns anything, the lockdown isn't working. (Web access is allowed only for the reference check at the end of the run, and only to HGNC and UniProt name lookups.)

If all four checks pass, go on to the inputs below, and record `lockdown: on` (with the `pathwiseLockdown` value from the settings file) as the first line of `pathwise_output/run_log.md` when the run log is created (see "Starting a run" in references/procedure.md).

If any check fails, **stop. Don't start the run, even if the user asks you to.** Tell the user, in plain words, that the lockdown isn't on, so the skill could be influenced by the internet, past chats, or old results, and that it won't run without it. Then give them these steps:

1. Download `pathway-extraction-workspace.zip` from the latest PathWise release (https://github.com/raptorpharmtox/PathWise/releases/latest) and unzip it.
2. In Claude Code, open the unzipped `pathway-extraction-workspace` folder itself, not a folder around it.
3. Put the PDFs in that folder's `papers` folder.
4. Start a new chat there and ask for the pathway again.

If only check 3 or 4 failed and the user is already in the workspace, tell them that the isolation hook didn't run, and that on Windows it needs Git for Windows (from git-scm.com) to be installed. Don't edit the settings file yourself.

The README's "Start here" section has the same steps with more detail.

## What this skill is not

It doesn't extract dose or exposure study parameters (it records which species an article says the evidence came from, but no doses, exposure details or numbers), and doesn't produce a narrative summary. If the user wants any of that, it's a different job — say so rather than quietly adding it.

## Required inputs — ask for these, don't wait for a pre-filled prompt

This skill is meant to be invoked with nothing more than "extract the pathway for X" — it is not a template the user fills in ahead of time. Unless the triggering message already states an input plainly, ask for it directly in chat before doing anything else. Don't guess, and don't start Step 1 on a partial set:

- **TOPIC** — required. The mechanism/subject to extract. Scope extraction strictly to this; if an article discusses other mechanisms in passing, ignore them. When TOPIC names more than one element (e.g. "X and Y"), a candidate key event or relationship must connect — directly, or through the chain — to every element named, not just one. Being related to only one half of a multi-part topic isn't enough to keep it; that's exactly how a plausible-looking but off-topic branch sneaks in (e.g. a CFTR-related mechanism that never actually touches oxidative stress, when the topic is "oxidative stress and CFTR").
- **TOPIC DESCRIPTION** — optional but ask for it anyway rather than skipping straight past it; the user can decline. A short 1-3 sentence elaboration of TOPIC's scope: which direction of causation, which mechanism type (e.g. genetic vs. acquired), which organ or exposure. Its only job is to disambiguate what counts as in-scope subject matter — it must never describe what the pathway's steps or structure should turn out to be. If it reads like a preview of key events in order, it's doing the wrong job and will bias extraction exactly the way the hard constraint above forbids; rewrite it as a boundary statement instead. Use it the same way as TOPIC itself when deciding whether something belongs.
- **ARTICLES** — required. A folder path (list every PDF in it, process in filename order) or an explicit ordered file list. If it's a folder, confirm with the user that it contains only the PDFs meant for this run — anything else sitting in there gets swept in too and processed as if it belonged. The lockdown only lets the skill read files inside the workspace, so the PDFs must be in it; the `papers` folder is the default. If the user points to PDFs outside the workspace, tell them to move or copy them into `papers` first.
- **ARTICLE SELECTION** — optional, but ask for it anyway; the user can skip it. Ask how the articles in this batch were chosen, as an open question they answer in their own words, and show an example so they know what's useful, e.g. "PubMed search: acetaminophen hepatotoxicity review, 2015–2025, free full text." Write their answer to `run_log.md` exactly as given (or `not given`). It's a record of how the evidence was collected, not an instruction: never use it to decide what to extract.
- **ONTOLOGY FILE** — path to the reference ontology JSON. If the user doesn't name one, ask whether they have an existing ontology file to reuse before defaulting to `pathwise_ontology.json` in the working directory — reusing their existing file is what makes terminology converge across separate runs, so don't default silently past one that already exists. Confirm whichever path is actually in play is present and readable before starting Step 1, since every term-alignment decision depends on it. If the user has no ontology file at all, that's fine: proceed with an empty one, so every term the run needs counts as new and goes into `new_terms.json`. The skill never creates or edits an ontology file itself.
- **EXTRACTION MODE** — required, and **ask this first**, before asking for TOPIC or the PDFs. Explain what the choice means before asking, in plain words. Don't assume the user knows what a "mode" or a "core chain" is. Say that Simplified records the basic cause-and-effect pathway, and Full also records extra details when an article mentions them (differences between species, factors like sex or genetics that change how strong an effect is, the stage of development when something happens, steps that only apply sometimes, and whether the trigger is genetic, chemical, or something else):
  - **Simplified** — the core MIE→KE→AO chain only (still includes per-KE/KER citation linking and the source-count tally — those aren't optional).
  - **Full** — simplified, plus capturing species-specific/conditional branching, confounders (including sex, age, diet and disease state), developmental-stage windows, initiating-event class (genetic/chemical/other), and record-keeping details (how a key event was measured, where the article says it likely applies, dose/timing/incidence patterns, the shape of the response, and how long one step takes to lead to the next), whenever the article states them.

  Tell the user that the choice changes what the skill looks for while it reads each article, and that it **can't be changed partway through or afterward**: if they choose Simplified and later want the extra detail, the only way to get it is to run the whole batch again. Don't default silently. See "Full mode only" in [references/article_agent.md](references/article_agent.md) for exactly what Full adds.

## Workflow overview

**Every article is extracted independently, by its own helper agent.** Once all the inputs are settled, launch one fresh helper agent per article, with identical instructions, as many at once as the session allows (in batches if needed). Each agent follows only [references/article_agent.md](references/article_agent.md) and sees only its own PDF and (when the ontology is small enough) the ontology file. It never sees another article or another agent's result, and the lockdown's isolation hook enforces that, so the order articles happen to run in can't change what any of them produces. Each agent reads its article completely, confirms it's relevant to TOPIC, extracts its pathway with verbatim evidence quotes and their citations, sets its terms, validates, writes its own result files into its own folder, and replies with a short status. A stopped run keeps every finished article and can be resumed.

**Only once every article agent has returned:** merge terms that share an ontology id; then have two independent clustering agents group the remaining terms that mean the same thing, key events first and relationships second, and separately suggest broader/narrower links between terms (never merged). Pairs both agents agree on are merged automatically, and pairs only one proposed are left for review. Pick each cluster's main term, then check every newly minted main term against the whole ontology file (this conversation searches the file for candidates, and two agents judge them), so a new term that duplicates an existing one is caught even if no article used the existing one. Save the clusters and the agents' agreement numbers, relabel, and build the tallied cross-article output.

The main skill's mechanics (starting and resuming a run, launching agents, merging, the tally and the reviews) are in **[references/procedure.md](references/procedure.md)**. Everything about extracting one article (naming rules, fields, quality assessments, the per-article file and examples) is in **[references/article_agent.md](references/article_agent.md)**. Read both before starting a run; they are the specification, not background reading.

## Talking to the user during and after a run

**During the run:** as each article agent returns, tell the user immediately if it failed to parse, was excluded as entirely off-topic, was borderline on-topic, was borderline and yielded zero key events, or was judged on-topic but yielded zero key events (the last two more prominently), each with its one-line reason. Say nothing for a normal article, and never mention partial exclusions, source type, adverse-outcome flags, single-source flags, or quality results. Details are in "Write your files and reply" in [references/article_agent.md](references/article_agent.md).

**After the batch (Step 8):** print a summary: key event and relationship totals, how many relationships have 2+ article support, the batch counts, a named recap of every flagged article with its reason, how many clusters were merged automatically and how much the two clustering agents agreed, how many new terms were matched to existing ontology terms, any feedback loops, any unspecified key events, the possible-duplicate pairs by name only, the relationship disagreements by their two key events, and, by name, any steps with conflicting evidence, steps an article says were disproved, timing or intensity conditions some papers state and others don't, species mismatches, methods an article calls experimental, and new relationship verbs. Single-source and single-citation counts, and undefined abbreviations, stay out of the summary. Then offer the four interactive checkpoints in order: review possible duplicates (including the pairs only one clustering agent proposed and possible matches to existing ontology terms), then review relationship disagreements (same meaning or different), then review the automatic clusters (split one, or change its main term), then review the suggested broader/narrower links (confirm or reject). Every decision is recorded in `new_terms.json` with who decided and when. Don't interpret the results or draw biological conclusions — that's for the human reviewing the output.

## What each output file is, for the user

The user will be looking at files in `pathwise_output/` whose names don't say much on their own. When handing off the results, make sure they know:

- **`articles/<pdf name>/<aop_id>.json`** (one per article with at least one key event, named like `cyp2e1@hepatocyte_necrosis_smith_2019.json`: initiating event, `@`, adverse outcome, then the article's name; the folder also holds that article's own new terms, undefined abbreviations, and an untouched `original/` copy) — that single article's extraction only: its key events (each with its level of organization and the species the evidence came from), relationships, quality notes on each (whether the article reports counterfactual evidence or attempts to disprove that step, and for relationships whether it explains how the step works, as `true`, `false`, or `"unknown"`, with the supporting quote for any `true` or `false`, and whether each disprove attempt supported or contradicted the step), any steps the article says were disproved (kept apart from the pathway), and a short list (at the very end of the file) of just the sources actually cited inside that evidence — not the article's full bibliography, which can run into the hundreds for a review article and would bury the pathway content. Written the moment that article finishes, so a stopped run still leaves complete, usable files behind for whichever articles got through.
- **`clusters.json`** — which terms were treated as the same concept and merged, the main term chosen for each cluster and why, the pairs left for review, and the suggested broader/narrower links between terms.
- **`undefined_abbreviations.json`** — abbreviations the articles never spelled out, gathered for a later definitions step. Not mentioned in the summary. `clustering/agreement.json` holds how much the two clustering agents agreed, with the full pair lists behind each number.
- **`run_log.md`** — whether the lockdown was on, the run status (`in progress`, `merging`, `reviewing`, `awaiting reference check` or `complete`), then one line per article: processed / excluded as off-topic / failed to open / no readable text, plus pages read. The first place to check if an expected article seems to be missing from the tally.
- **`reference_check.json`** — written by the `reference-check` skill at the end: the date, the HGNC version, and for each gene or protein part of a key event name whether it was confirmed, renamed (with the reason), not found or left for the user, with its HGNC id and UniProt accession.
- **`new_terms.json`** — every ontology term minted this run (each with an id, a display label and a short definition), unreviewed, plus which article(s) prompted it, and new wordings to add to existing ontology terms as synonyms. Anything with `possible_duplicate_of` is the run flagging its own uncertainty — a human call, not a resolved merge. If the user did the end-of-run reviews, it also holds `resolved_duplicates`, `resolved_relationship_disagreements`, and `resolved_clusters`: each decision, the original reason, who decided, and when.
- **`merged_tally.json`** — the actual deliverable: every key event/relationship merged across articles with an `article_count` (how many articles support it) and a separate `distinct_sources_cited` count (how many distinct primary references those articles cite as evidence for it — not the same number, since several articles can cite the same primary source, or one article can cite several), plus flag arrays: `single_source_flags` (backed by only one article), `single_citation_flags` (backed by several articles, but all citing the same one source), `relationship_disagreement_flags` (two articles connect the same two key events but don't use exactly the same pair of tags, like "activates" versus "inhibits"), `detail_difference_flags` (the same, but one article only said `unknown`), `ambiguous_source_matches` (cited papers matched on author and year only, or likely the same paper with different years), `conflicting_evidence_flags` (steps an article still asserts while reporting a test against them), `disproved_step_flags` (steps an article says were disproved, and whether another supports them), `species_mismatch_flags`, `experimental_method_flags`, and `condition_flags` (a timing or intensity condition some papers state and others don't), plus `unspecified_terms` (key events whose name doesn't say what to measure, because the article never said) and `feedback_loops` (loops, and feedforward the articles name, with how many articles describe each). All are a "look here," not a verdict on whether it's a real disagreement or an extraction miss. In Full mode, entries also carry a `layers` tag (`species_conditional`, `circumstance_conditional`, `genetic_conditional`, `confounder`, `developmental_window`) wherever the source article states that kind of qualifier, plus the underlying detail (species annotations, confounder descriptions, developmental windows, initiating-event class, and the record-keeping fields: how each key event was measured, stated applicability, concordance, response shape and time scale) — all still tied to a verbatim quote, never inferred.

See "What each output file is, in plain language" in [references/procedure.md](references/procedure.md) if the user wants the fuller version of this.
