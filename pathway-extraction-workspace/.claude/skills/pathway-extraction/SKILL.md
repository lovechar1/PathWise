# PathWise Ontology Extraction

## The one rule that overrides everything else below

**Every key event and relationship must come from what the article you're currently reading actually says — full stop.** If you recognize the general mechanism from training data, the AOP-Wiki, a textbook, or any other article, that recognition must never fill a gap, resolve an ambiguity, order the steps, or shape the structure. If an article is vague, incomplete, or organizes something unexpectedly, extract it exactly that way — vague or unusual — rather than smoothing it into the version you already expect. If you can't point to a specific quoted passage supporting a candidate key event or relationship, leave it out.

This extends specifically to the AOP-Wiki: never search it, never check whether a matching pathway already exists there, never let its structure influence what you extract, and never look it up at all during extraction — not even to borrow wording for a term. There is no exception at any point in a run. The reason a "just for wording" carve-out doesn't work: looking up a key event on AOP-Wiki necessarily surfaces the whole entry — its upstream/downstream events, the pathways it belongs to — and once that's in context, "don't let it influence structure" is asking you not to be influenced by something you've already read. The lookup itself creates the exposure it's supposed to prevent.

Why this matters: the entire point of this pipeline is to surface pathways that may be new, or that branch differently from what's already registered. Treating an existing AOP (or your own prior knowledge of "how this pathway usually goes") as ground truth defeats that purpose before the run even starts.

PathWise builds its own ontology instead: every new term is minted from the articles' own wording and recorded in `new_terms.json` for a human to review. No outside ontology or database is checked, not even at the end of a run.

## Before anything else: confirm the lockdown is on

This skill must only run inside the PathWise lockdown workspace (the `pathway-extraction-workspace` folder from the PathWise repository). Its settings file blocks the internet, shell commands, past chats, saved memory, and every folder outside the workspace, so nothing but the PDFs supplied for this run can shape the extraction. Check this first, before asking for EXTRACTION MODE or anything else:

1. Read `.claude/settings.json` in the current working directory. It must exist and contain `"pathwiseLockdown"`.
2. Use ToolSearch with `select:WebSearch,WebFetch,Bash,PowerShell`. None of them should be available. If any of them is, the lockdown isn't working.
3. Check that helper agents are isolated. Launch one helper agent (the Agent tool, general-purpose, fresh) with the prompt: "Use the Read tool on `pathwise_output_canary.txt` in the current folder. If the read is refused, reply exactly `REFUSED` followed by the refusal message. If it works, reply exactly `READ`. Do nothing else." The check passes only if the reply starts with `REFUSED`. A reply of `READ`, anything else, or no reply means the isolation hook isn't working, so helper agents could see each other's results.

If all three checks pass, go on to the inputs below, and record `lockdown: on` (with the `pathwiseLockdown` value from the settings file) as the first line of `pathwise_output/run_log.md` when the run log is created in Step 1.

If any check fails, **stop. Don't start the run, even if the user asks you to.** Tell the user, in plain words, that the lockdown isn't on, so the skill could be influenced by the internet, past chats, or old results, and that it won't run without it. Then give them these steps:

1. Download the PathWise repository from GitHub (green **Code** button, then **Download ZIP**) and unzip it.
2. In Claude Code, open the `pathway-extraction-workspace` folder from inside it. Open that folder itself, not the repository folder around it.
3. Put the PDFs in that folder's `papers` folder.
4. Start a new chat there and ask for the pathway again.

If only check 3 failed and the user is already in the workspace, tell them that the isolation hook didn't run, and that on Windows it needs Git for Windows (from git-scm.com) to be installed. Don't edit the settings file yourself.

The README's "Start here" section has the same steps with more detail.

## What this skill is not

It doesn't extract dose/species/exposure study parameters, and doesn't produce a narrative summary. If the user wants any of that, it's a different job — say so rather than quietly adding it.

## Required inputs — ask for these, don't wait for a pre-filled prompt

This skill is meant to be invoked with nothing more than "extract the pathway for X" — it is not a template the user fills in ahead of time. Unless the triggering message already states an input plainly, ask for it directly in chat before doing anything else. Don't guess, and don't start Step 1 on a partial set:

- **TOPIC** — required. The mechanism/subject to extract. Scope extraction strictly to this; if an article discusses other mechanisms in passing, ignore them. When TOPIC names more than one element (e.g. "X and Y"), a candidate key event or relationship must connect — directly, or through the chain — to every element named, not just one. Being related to only one half of a multi-part topic isn't enough to keep it; that's exactly how a plausible-looking but off-topic branch sneaks in (e.g. a CFTR-related mechanism that never actually touches oxidative stress, when the topic is "oxidative stress and CFTR").
- **TOPIC DESCRIPTION** — optional but ask for it anyway rather than skipping straight past it; the user can decline. A short 1-3 sentence elaboration of TOPIC's scope: which direction of causation, which mechanism type (e.g. genetic vs. acquired), which organ or exposure. Its only job is to disambiguate what counts as in-scope subject matter — it must never describe what the pathway's steps or structure should turn out to be. If it reads like a preview of key events in order, it's doing the wrong job and will bias extraction exactly the way the hard constraint above forbids; rewrite it as a boundary statement instead. Use it the same way as TOPIC itself when deciding whether something belongs.
- **ARTICLES** — required. A folder path (list every PDF in it, process in filename order) or an explicit ordered file list. If it's a folder, confirm with the user that it contains only the PDFs meant for this run — anything else sitting in there gets swept in too and processed as if it belonged. The lockdown only lets the skill read files inside the workspace, so the PDFs must be in it; the `papers` folder is the default. If the user points to PDFs outside the workspace, tell them to move or copy them into `papers` first.
- **ONTOLOGY FILE** — path to the reference ontology JSON. If the user doesn't name one, ask whether they have an existing ontology file to reuse before defaulting to `pathwise_ontology.json` in the working directory — reusing their existing file is what makes terminology converge across separate runs, so don't default silently past one that already exists. Confirm whichever path is actually in play is present and readable before starting Step 1, since every term-alignment decision depends on it. If the user has no ontology file at all, that's fine: proceed with an empty one, so every term the run needs counts as new and goes into `new_terms.json`. The skill never creates or edits an ontology file itself.
- **EXTRACTION MODE** — required, and **ask this first**, before asking for TOPIC or the PDFs. Explain what the choice means before asking, in plain words. Don't assume the user knows what a "mode" or a "core chain" is. Say that Simplified records the basic cause-and-effect pathway, and Full also records extra details when an article mentions them (differences between species, factors like sex or genetics that change how strong an effect is, the stage of development when something happens, steps that only apply sometimes, and whether the trigger is genetic, chemical, or something else):
  - **Simplified** — the core MIE→KE→AO chain only (still includes per-KE/KER citation linking and the source-count tally — those aren't optional).
  - **Full** — simplified, plus capturing species-specific/conditional branching, confounders, developmental-stage windows, and initiating-event class (genetic/chemical/other), whenever the article states them.

  Tell the user that the choice changes what the skill looks for while it reads each article, and that it **can't be changed partway through or afterward**: if they choose Simplified and later want the extra detail, the only way to get it is to run the whole batch again. Don't default silently. See "Extraction mode: Simplified vs. Full" in [references/procedure.md](references/procedure.md) for exactly what each mode does and doesn't capture.

## Workflow overview

**Every article is extracted independently, by its own helper agent.** Once all the inputs are settled, launch one fresh helper agent per article, with identical instructions, as many at once as the session allows (in batches if needed). Each agent sees only its own PDF, this skill's files, and the ontology file. It never sees another article or another agent's result, and the lockdown's isolation hook enforces that, so the order articles happen to run in can't change what any of them produces. Each agent reads its article completely (chunked, max 20 pages per call), confirms it's relevant to TOPIC, extracts its pathway paragraph-by-paragraph with verbatim evidence quotes, pulls its bibliographic metadata and cited references, aligns every term against the ontology file only, validates, and returns its result. This conversation writes each result to disk the moment it arrives, so a stopped run keeps every finished article and can be resumed.

**Only once every article agent has returned:** merge terms that share an ontology id; then have two independent clustering agents group the remaining terms that mean the same thing, key events first and relationships second. Pairs both agents agree on are merged automatically, and pairs only one proposed are left for review. Save the clusters and the agents' agreement numbers, pick each cluster's main term, relabel, and build the tallied cross-article output.

The full mechanics — the relevance check, exact JSON schemas, the granularity-anchoring reference example, the terminology-alignment decision procedure, validation checklist, and merge logic — are in **[references/procedure.md](references/procedure.md)**. Read it before starting Step 1 of an actual run; it is not optional background reading, it's the specification.

## Talking to the user during and after a run

**During the run:** as each article agent returns, tell the user immediately if it failed to parse, was excluded as entirely off-topic, was borderline on-topic, was borderline and yielded zero key events, or was judged on-topic but yielded zero key events (the last two more prominently), each with its one-line reason. Say nothing for a normal article, and never mention partial exclusions, source type, adverse-outcome flags, single-source flags, or quality results. Details are in "Per-article callouts" in [references/procedure.md](references/procedure.md).

**After the batch (Step 8):** print a summary: key event and relationship totals, how many relationships have 2+ article support, the batch counts, a named recap of every flagged article with its reason, how many clusters were merged automatically and how much the two clustering agents agreed, the possible-duplicate pairs by name only, and the relationship disagreements by their two key events. Single-source and single-citation counts stay out of the summary. Then offer the three interactive checkpoints in order: review possible duplicates (including the pairs only one clustering agent proposed), then review relationship disagreements (same meaning or different), then review the automatic clusters (split one, or change its main term). Every decision is recorded in `new_terms.json` with who decided and when. Don't interpret the results or draw biological conclusions — that's for the human reviewing the output.

## What each output file is, for the user

The user will be looking at files in `pathwise_output/` whose names don't say much on their own. When handing off the results, make sure they know:

- **`<aop_id>.json`** (one per article, named like `cyp2e1@hepatocyte_necrosis_smith_2019.json`: initiating event, `@`, adverse outcome, then the article's name) — that single article's extraction only: its key events, relationships, two quality notes on each (whether the article reports counterfactual evidence or attempts to disprove that step, as `true`, `false`, or `"unknown"`, with the supporting quote for any `true` or `false`), and a short list (at the very end of the file) of just the sources actually cited inside that evidence — not the article's full bibliography, which can run into the hundreds for a review article and would bury the pathway content. Written the moment that article finishes, so a stopped run still leaves complete, usable files behind for whichever articles got through.
- **`clusters.json`** — which terms were treated as the same concept and merged, the main term chosen for each cluster and why, and the pairs left for review. `clustering/agreement.json` holds how much the two clustering agents agreed, with the full pair lists behind each number.
- **`run_log.md`** — whether the lockdown was on, then one line per article: processed / excluded as off-topic / failed to open / no readable text, plus pages read. The first place to check if an expected article seems to be missing from the tally.
- **`new_terms.json`** — every ontology term minted this run, unreviewed, plus which article(s) prompted it. Anything with `possible_duplicate_of` is the run flagging its own uncertainty — a human call, not a resolved merge. If the user did the end-of-run reviews, it also holds `resolved_duplicates`, `resolved_relationship_disagreements`, and `resolved_clusters`: each decision, the original reason, who decided, and when.
- **`merged_tally.json`** — the actual deliverable: every key event/relationship merged across articles with an `article_count` (how many articles support it) and a separate `distinct_sources_cited` count (how many distinct primary references those articles cite as evidence for it — not the same number, since several articles can cite the same primary source, or one article can cite several), plus four flag arrays: `single_source_flags` (backed by only one article, where others clearly discuss the same region), `single_citation_flags` (backed by several articles, but all citing the same one source), `relationship_disagreement_flags` (two articles connect the same two key events but don't use exactly the same pair of tags, like "activates" versus "inhibits"), and `ambiguous_source_matches` (cited papers matched on author and year only, or likely the same paper with different years). All are a "look here," not a verdict on whether it's a real disagreement or an extraction miss. In Full mode, entries also carry a `layers` tag (`species_conditional`, `confounder`, `developmental_window`) wherever the source article states that kind of qualifier, plus the underlying detail (species annotations, confounder descriptions, developmental windows, initiating-event class) — all still tied to a verbatim quote, never inferred.

See "What each output file is, in plain language" in [references/procedure.md](references/procedure.md) if the user wants the fuller version of this.
